% 3 -- Problem Statement & Motivation
\begin{frame}{Problem Statement \& Motivation}
\small
\begin{block}{Problem Statement}
Most municipal waste routes are \textbf{fixed in advance} and never actually reflect the shortest path between homes, bins, and the depot -- so trucks burn extra fuel, take longer, and tie up more staff than they need to. Hazardous waste rides along on the same route as ordinary trash, even though it really needs immediate, zone-restricted pickup, and because schedules run on a fixed calendar, some bins get emptied too often while others overflow between visits.
\end{block}
\vspace{0.7mm}
\textbf{\color{GEUBlue}Motivation}
\begin{itemize}\itemsep2pt
\item Fixed routes don't account for the city's actual road network, so trucks aren't taking the shortest path
\item Hazardous waste needs to be disposed of immediately, not left to wait its turn, and routed clear of residential areas rather than trucked straight through them
\item Calendar-based pickups send labor to bins that aren't even close to full
\end{itemize}
\end{frame}

\begin{frame}{Target Users \& Stakeholders}
\textbf{\color{GEUBlue}Who This Is Built For}
\vspace{2mm}
\begin{itemize}\itemsep6pt
\item Municipal waste departments and truck operators
\item Residents and commercial establishments on the route
\item Public health -- getting hazardous waste cleared faster and more safely
\end{itemize}
\end{frame}

% 4 -- Objectives
\begin{frame}{Objectives}
\textbf{\color{GEUBlue}Project Objectives}
\vspace{1mm}
\begin{enumerate}\itemsep4pt
\item Represent the city as a weighted graph, with the depot, homes, junctions, and bins as nodes, each one tagged by zone type -- residential, commercial, or industrial.
\item Work out collection routes with Dijkstra's algorithm, letting the truck switch between two modes as needed: Priority or FIFO.
\item Flag hazardous waste the moment it's detected and send it straight out on a zone-constrained path that steers clear of residential and commercial areas.
\item Base collection frequency on how full a bin actually is, not on a fixed calendar.
\item Put all of this behind a REST API, with the route computation playing out live and animated on the web frontend.
\end{enumerate}
\end{frame}

% 5 -- Proposed Solution: Approach
\begin{frame}{Proposed Solution -- Approach}
\small
\textbf{\color{GEUBlue}Proposed Approach}
\vspace{1mm}
\begin{enumerate}\itemsep3pt
\item \textbf{City layout} -- at startup, the server reads the depot, homes, junctions, bins, and their zone tags straight from a JSON config file.
\item \textbf{Routing engine} -- shortest paths between any two nodes come from Dijkstra's algorithm, run in either a plain or a zone-constrained variant.
\item \textbf{Route builders} -- multi-stop collection runs get sequenced by whichever strategy is active, Priority or FIFO.
\item \textbf{Scheduler} -- a location's fill-rate and how long it's been since its last pickup decide whether it's due for a visit.
\item \textbf{Delivery} -- everything comes back as JSON over a REST API and plays out live in a React frontend built with Cytoscape.js.
\end{enumerate}
\vfill
\smallnote{One persistent C++ HTTP server holds the graph and handles routing, classification, and scheduling end to end.}
\end{frame}

% 13 -- Dijkstra's Algorithm: How It Works
\begin{frame}{Dijkstra's Algorithm -- How It Works}
\footnotesize
\begin{center}
\begin{tikzpicture}[
node distance=5mm,
box/.style={rectangle,rounded corners,draw=GEUBlue,fill=GEULightBlue,minimum width=1.95cm,minimum height=9mm,align=center,font=\tiny},
arrow/.style={-{Latex[length=2mm]},thick,draw=GEUBlue}
]
\node[box] (a) {Init \texttt{dist[]},\\push source};
\node[box,right=of a] (b) {Pop min-\\dist node $u$};
\node[box,right=of b] (c) {Relax\\edges of $u$};
\node[box,right=of c] (d) {Reconstruct\\path};
\draw[arrow] (a)--(b);
\draw[arrow] (b)--(c);
\draw[arrow] (c)--(d);
\draw[arrow] (c.north) to[out=90,in=90] node[midway,above,font=\tiny]{repeat} (b.north);
\end{tikzpicture}
\end{center}
\vspace{1mm}
\begin{enumerate}\itemsep2pt
\item Set \texttt{dist[source]=0} and everything else to $\infty$, then push the source into a min-heap keyed by distance.
\item Pop whichever node \texttt{u} currently has the smallest tentative distance.
\item \textbf{Relax} edge \texttt{(u,v,w)}: if \texttt{dist[u]+w} beats \texttt{dist[v]}, update \texttt{dist[v]} and push \texttt{v}.
\item Walk the predecessor map back to the source to reconstruct the path.
\end{enumerate}
\vfill
\smallnote{Complexity: $O((V+E)\log V)$ with a binary heap.}
\end{frame}

% 15 -- Fill-Rate & Frequency Management: Formula
\begin{frame}[fragile]{Fill-Rate \& Frequency Management -- Interval Formula}
\footnotesize
Each home or bin stores \texttt{fillRate} (units/day), \texttt{capacity}, and \texttt{lastCollected}. From these, the scheduler works out a visit interval per location:
\vspace{1mm}
\begin{center}
\colorbox{GEULightBlue}{\parbox{.7\textwidth}{\centering
\texttt{interval\_days = capacity / fillRate}, clamped to $[1, 14]$ days}}
\end{center}
\vspace{1mm}
\begin{center}
\begin{tikzpicture}[font=\scriptsize]
\draw[thick,GEUBlue,-{Latex[length=2mm]}] (0,0) -- (10.5,0);
\draw[thick,GEUBlue] (0,0.15) -- (0,-0.15) node[below,yshift=-1mm]{lastCollected};
\draw[thick,GEUBlue] (5,0.15) -- (5,-0.15) node[below,yshift=-1mm]{due (+interval)};
\draw[thick,red] (8,0.15) -- (8,-0.15) node[below,yshift=-1mm]{now};
\draw[decorate,decoration={brace,amplitude=4pt},thick,red] (5,0.4) -- (8,0.4) node[midway,above,yshift=2mm]{overdue-ness $\to$ max-heap rank};
\node[above,font=\tiny] at (2.5,0) {interval\_days};
\end{tikzpicture}
\end{center}
\begin{itemize}\itemsep1pt
\item A \textbf{floor of 1 day} keeps a fast-filling bin from demanding more than one visit per day
\item A \textbf{ceiling of 14 days} means no location ever waits more than two weeks, no matter how slowly it fills
\item A location becomes due once \texttt{now} $\ge$ \texttt{lastCollected + interval\_days}; visiting it calls \texttt{markCollected()}, which resets \texttt{lastCollected} to now
\end{itemize}
\end{frame}

% 18 -- REST API: How It Works & Design
\begin{frame}{REST API -- How It Works \& Design}
\small
The frontend and backend communicate over plain HTTP: the browser sends a JSON request to a resource path, the C++ server responds with a JSON body -- no session state is kept on either side between calls.
